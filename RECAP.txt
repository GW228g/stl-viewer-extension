STL VIEWER FOR GOOGLE CLASSROOM — PROJECT RECAP
For Claude Code handoff · current for v1.4.2 (2026-10-08)
=========================================================

WHAT THIS IS
------------
A Chrome extension (Manifest V3) that adds a "View in 3D" button to Google Classroom
(and Google Drive) whenever an STL file can't be previewed. Clicking it opens a
full-screen WebGL viewer in the browser — no downloading, no Tinkercad, no slicer.
Along with the model it shows dimensions, volume and estimated filament weight, and a
floating-geometry check, and it can save the view as a PNG to send back to a student.

Built for James, a Tech Ed teacher at East Lyme Middle School in Niantic CT, who runs
a 3D printing unit where students design keychains in Tinkercad and submit STL files
via Google Classroom. Reviewing 30 submissions by downloading each file individually
was the problem this solves.

Intended to be published to the Chrome Web Store under the Maker404 brand
(maker404.com — James's free K-6 educator resource site). NOT YET SUBMITTED.

HOW IT WORKS — STEP BY STEP
---------------------------
1. content.js runs on classroom.google.com, drive.google.com, docs.google.com
   (all_frames: true, because the file viewer can sit in an iframe).
2. A MutationObserver plus a 30-second polling safety net (tryInject) watch for the
   text "No preview available". The "injected" flag resets when the URL changes, so
   moving between student submissions works without a page reload.
3. findDownloadUrl() resolves the file, trying in order:
     a. an anchor whose href contains ".stl"
     b. an anchor with export=download or drive.google.com/uc
     c. a Drive file ID from an iframe src
     d. a Drive file ID from the page URL
     e. a Drive file ID from data-id / data-fileid / data-docid attributes
        (prefers an aria-selected element)
     f. last resort: any anchor whose text contains "download", EXCLUDING Google's own
        help/account hosts (NON_FILE_HOSTS). That exclusion fixed a real bug where a
        support.google.com article was fetched instead of the file.
   The URL is re-resolved on every click, not cached, so "Try Again" re-scans.
4. A "View in 3D" button is appended below the "No preview available" box.
5. Click → chrome.runtime.sendMessage({type:'FETCH_STL'}) → background.js fetches,
   base64-encodes in 32 KB chunks (call-stack safety) and replies
   {ok, b64, filename}. Errors: HTTP status, or "Got an HTML page" (not signed in).
6. content.js decodes, parseSTL() → openViewer(stl, fileName).
7. The viewer opens at once. The floating check runs ~50 ms later (setTimeout, not
   requestAnimationFrame — rAF is paused in a hidden tab) and fills in a toolbar pill.
The STL never touches disk. GPU buffers are released when the viewer closes (the render
loop stops itself when the overlay leaves the DOM).


ORIENTATION  (determineUpAxis)
------------------------------
STL has no orientation metadata. Tinkercad — and 3D printing in general — is Z-up;
the WebGL scene is Y-up. So Z is the default "up" axis (rotX(-90°) maps Z to Y).
Exception: a flat plaque (a keychain) whose thickness was authored along another axis.
That axis is treated as up only if it is at most half the next-smallest dimension.
The same function picks the floor axis for the floating check.
History worth knowing: the original heuristic ("thinnest axis is up") tipped tall
models (lighthouses, 3DBenchy) onto their side. Thresholding it wasn't enough — models
with no clearly thin axis still fell back to "Y is up", which was wrong. The fix was
to default to Z-up. A model the student rotated on its side in Tinkercad shows as
exported; that is deliberate (it's how it would print). Users can drag to rotate.


FLOATING-GEOMETRY CHECK  (detectFloating)
-----------------------------------------
1. Union-find on triangles that share a vertex. Vertices are quantised to a grid of
   tol/2 (tol = 1.5% of the model's largest dimension), so tiny gaps count as connected.
2. Each connected piece gets a bounding box.
3. A piece is SUPPORTED if its floor-axis minimum is within tol of the global minimum
   (it reaches the bed), or if its bounding box overlaps (±tol) a supported piece.
   Support spreads through chains of overlapping pieces (BFS).
4. Any unsupported piece = floating.
Why the overlap rule: separate shells that are embedded in the body (inlaid lettering,
artwork layers, nested parts) never touch the bed but print fine. Before 1.4.2 they were
all flagged — 6 of 41 real STLs, none visibly floating.
Toolbar pill states: checking → clear (green) | floating (orange) | skipped | failed.
"Skipped" = over MAX_FLOAT_CHECK_TRIS (1,000,000). Over MAX_PIECES_FOR_OVERLAP_TEST
(5,000 pieces) the overlap test is skipped, falling back to "any piece off the bed".
Speed: ~0.25 ms per 1,000 triangles (864,500 triangles ≈ 190 ms). The old 200,000 cap
was needlessly cautious and silently skipped normal models like 3DBenchy.
KNOWN LIMIT: bounding-box overlap can't see a part floating INSIDE a hollow body, or
in the empty corner of an L-shaped one. Accepted trade-off.


VOLUME AND WEIGHT
-----------------
meshVolume(): signed tetrahedron sums (independent of winding and of where the model
sits). meshSurfaceArea(): half the cross-product magnitudes.
estimateGrams = ( shell + (volume − shell) × infill ) × density, where
shell = min(volume, surfaceArea × SHELL_MM) and SHELL_MM = 1.2 (≈3 walls + top/bottom).
A plain volume × infill% would badly under-weigh thin parts like keychains, which are
almost all shell — so those barely change with infill, as in a slicer.
MATERIALS = { PLA: 1.24, PETG: 1.27 } g/cm³; adding one is a one-line change.
Infill 10–100% in steps of 10, default 20%. The last material/infill choice is kept in
module variables for the page session only — NO storage permission on purpose.
Assumes millimetre units and a watertight mesh. Weight is hidden when the volume is
~0 (an open surface, or a file exported in metres). It's a rough guide; detailed meshes
inflate surface area, which biases the estimate high.


VIEWER / TOOLBAR
----------------
Custom WebGL, no dependencies: lit model shader + flat grid shader, two directional
lights, column-major m4 matrix object. Drag = rotate, Shift+drag = pan, scroll = zoom,
Reset View. The grid is drawn at the model's floor; the model MVP is centre → autoRot →
user rotation, the grid MVP is user rotation only (otherwise autoRot is applied twice).
Toolbar, left to right: printer icon · "STL Preview" · triangle count · W×D×H mm (print
orientation) · volume · weight · material · infill · floating pill · hint · Reset ·
Save PNG · Close.
Layout: min-height 52 px, flex-wrap. The hint has zero flex-basis and shrinks away first;
then the three buttons wrap together to a second row. Checked 600–1366 px: nothing is
ever pushed off-screen. (Earlier the bar needed ~1100 px and clipped Close.)
Toolbar text colours: the hint was once #2d3154 on #0a0b10 — unreadable. Keep it at
#8892c8.


SAVE PNG
--------
Composites a 52 px header (title, triangles, dimensions, volume/weight "of PETG at 20%
infill", floating pill in whatever state it's in) above the canvas
(preserveDrawingBuffer: true). Downloads as "<student file name>-screenshot.png".
Name source: Content-Disposition (filenameFromDisposition prefers RFC 5987 filename*,
falls back to the plain form if the escape is malformed) → an .stl link → ".stl" text
on the page → "stl-preview-screenshot.png". Illegal characters and path parts are
stripped. The page-text fallback is a guess and can pick up neighbouring label text;
it only runs when Drive sends no header (unverified against real Drive headers).


STL PARSER
----------
Binary vs ASCII is decided by exact byte length (84 + nTri × 50), else a "facet normal"
keyword; a binary fallback accepts files at least the expected size. If stored normals
are all zero (some CAD tools), face normals are computed from edge cross products.


PERMISSIONS  (see CHROMEWEBSTORE.md for the justifications)
-----------
No "permissions" array at all. host_permissions:
  classroom.google.com, drive.google.com, drive.usercontent.google.com,
  docs.google.com, *.googleusercontent.com
Content-script matches: classroom, drive, docs only.
History: it used to include *.google.com and *.googleapis.com — unused and the sort of
thing Store review flags. Removing them broke downloads ("Failed to fetch") because
Drive redirects uc?export=download to drive.usercontent.google.com, which is NOT covered
by *.googleusercontent.com (different domain). That one was added back by name.

TESTING
-------
There is no test framework in the repo. What has worked (the harness lives outside the
repo; recreate it as needed):
  - Node: pull a function out of content.js by brace-matching its source text and run it
    on real STLs (volume, orientation, floating). Compare old vs new behaviour on every
    STL in ~/Downloads. content.js is an IIFE, so there is nothing to require().
  - Real viewer: serve a page over HTTP that contains the text "No preview available",
    a hidden <a href="https://drive.google.com/uc?export=download&id=AAAA…">, a stub
    window.chrome.runtime.sendMessage returning {ok:true, b64, filename}, and
    <script src="content.js">. Drive it with headless Chrome over the DevTools protocol
    (/Applications/Google Chrome.app, --headless=new --use-angle=swiftshader
    --enable-unsafe-swiftshader, Emulation.setDeviceMetricsOverride for an exact size).
    Click the button, find the toolbar (the div with style.minHeight === '52px'), read
    its spans, click Save PNG and read the intercepted anchor's download name.
  - The same setup produces the 1280x800 Store screenshots.
Never claim a UI change works from "node --check" alone.


GOTCHAS
-------
- chrome:// pages can't be automated. After a code change James must click reload on the
  extension card at chrome://extensions, THEN reload the Drive/Classroom tab (content
  scripts only inject on page load).
- Chrome Sync doesn't sync unpacked extensions; each computer needs a manual install.
- The built-in browser pane shows file:// pages as static snapshots — serve over HTTP.
- macOS: sed needs -i '' ; there is no `timeout` command; screenshot file names contain
  a narrow no-break space (U+202F) before AM/PM, so quoted paths fail — use a glob.
- Don't run two Claude sessions in the same folder. A test server's .claude/launch.json
  once got committed onto the dev branch by the other session. It's gitignored on main
  now; use a separate git worktree for a second line of work.
- Verify before asserting: several "obvious" causes here turned out wrong (the
  "Failed to fetch" was a missing host permission; the console errors on Drive were
  another extension's). Look at the actual error and the actual file.


KNOWN LIMITATIONS
-----------------
- Only works as an unpacked developer extension for now.
- Mouse only; no touch or stylus rotation.
- Floating check: bounding-box overlap limit above; skipped over 1M triangles.
- Weight: PLA/PETG only, a rough guide, assumes mm units and a watertight mesh.
- Orientation assumes Tinkercad's Z-up; a model exported on its side shows that way.
- If the student's Google account can't read the Drive file, the fetch fails with a
  message in the button's status line.
